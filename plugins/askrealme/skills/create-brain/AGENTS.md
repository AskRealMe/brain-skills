# Create Brain writing rules

Apply these rules to `SKILL.md`, `README.md`, and files under `references/`.

- Write for a reader who did not see the conversation that produced the text.
- Describe the final behavior, not rejected alternatives or intermediate
  debugging history.
- Use established terms. Avoid invented labels and metaphors.
- Use active voice and present tense. Keep one main claim per sentence.
- Put conditions before instructions.
- Use adjectives such as "recommended," "faster," or "better" only when
  evidence supports them.
- Keep one canonical home per fact. Point to a specific file and heading or
  symbol instead of copying changing values.
- `SKILL.md` owns the executable workflow. `README.md` owns design rationale.
  Reference files own detailed conditional contracts.
- Product output describes experiences and usable practices, not its own
  production process.
- When behavior changes, update its frontmatter description, references, tests,
  and user-facing copy together.
